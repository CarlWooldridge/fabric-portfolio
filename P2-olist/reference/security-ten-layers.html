Security in Fabric: ten layers, and where each is enforced

Every layer here was built and then tested by signing in as a real user, not the workspace admin. The pattern that came out of it: each layer is enforced by specific engines, and each one has a path around it.

Part 1

The ten layers

Read a requirement for the layer it names, then answer from that layer. The most common mistake, on the practice exam and in design reviews, is answering a data question with a workspace role.

2Workspace rolesWho gets into the workspaceThe workspaceToo coarse for "protect data". Admin, Member and Contributor read everything

4T-SQL GRANT / DENYWhich objectsWarehouse / SQL endpoint (delegated mode)"specific objects in the warehouse"

10Sensitivity labelsClassification that travels. Not access controlEvery item, inherited downstream"classify for compliance"
 Three rules that sit across the table: model RLS is default-deny (once a model has any role, a Viewer in none is refused); roles add up (a user in two roles sees the union); and hidden is not secured (a hidden table is still queryable; OLS makes it not exist).

Two ways to hand out everything

ReadAll on a warehouse undoes its T-SQL security for that user: Spark and Direct Lake on OneLake read the files directly.

A delegated-identity shortcut hands every reader the creator's access. A test user holding only Read and ReadData on the warehouse read all 5 rows through one, unfiltered and unmasked, from Spark and from SQL. The passthrough shortcut refused until ReadAll was granted, then returned all 5 too. Warehouse RLS, CLS and masking never travel through any shortcut.

Part 5

Gotchas that cost time

What happenedWhat it means
Permission changes took up to two hours to reach SQLHours went to chasing lag. Wait, re-test, then theorize. OneLake role changes reach the SQL endpoint through a security sync of about five minutes, as OLS_ roles.
Contributor flipped reports to unmasked while direct SQL stayed maskedElevated roles confound every test. Test as a real Viewer.
A UPN differing only in case silently failed RLSFabric Warehouse collation is case-sensitive. Compare with LOWER().
WHERE salary BETWEEN 90000 AND 92000 found a row displayed as 0Masking hides values, not rows. It isn't access control.
Mapping-table RLS returned 0 rows for an unmapped userIt fails closed. DENY on the mapping table doesn't break the predicate (ownership chaining).
The lakehouse endpoint refused GRANT with Msg 19830It's in user's-identity mode, so T-SQL permissions don't apply there. A free mode check. Masking still works.
An external guest's visuals failed until fixed identityFixed identity then applies to every viewer and blinds the source to who's asking. Row rules have to move into the model.
A seller role left orders, customers and payments unfilteredRLS filters flow down relationships, not up. Put the rule on the table at the top of what you protect.
A role's own filter read a table that role hides with OLSOLS secures what the user can query, not what the role's DAX can reference.
An OLS-secured field silently dropped out of a field-parameter visualDirectly, OLS errors the visual. Through a field parameter it fails quietly.
Removing a sensitivity label upstream left it on everything downstreamLabels inherit forward and don't un-inherit.
Every lakehouse carried a DefaultReader OneLake roleRoles add up (a union), so a restrictive role only restricts users who aren't also covered by DefaultReader.
