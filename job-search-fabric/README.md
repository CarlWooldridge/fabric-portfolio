# Job Search — an AI evaluation pipeline, productionized on Microsoft Fabric

**Goal:** take a workflow I actually run every day — an AI-assisted evaluation of inbound job postings — and put it on Fabric properly: governed storage, a Direct Lake semantic model, and a report I can *write back* from, rather than a dashboard I only look at.

**Why this one is different from P1.** [P1](../P1-nyc-taxi/) was a public dataset chosen to exercise mechanisms. This is a system with a real user, real consequences when it breaks, and data that arrives messy because a language model wrote it. It is also the only project here where I lost data and had to recover it.

**Environment:** Fabric trial capacity (East US). Lakehouse `JobSearch_LH`, Fabric SQL Database `JobSearch_DB`, Dataflow Gen2 `JD_Transform`, semantic model `Job Search Model`, User Data Function `JD_ActionWriteback`, six-page Power BI report.

**Scale at time of writing:** 1,066 evaluated postings across 676 distinct employers, 6,169 score-component rows, 19 recruiter message threads, 23 recorded write-backs.

> **On the data in this repository.** Everything under `data-samples/` is synthetic, generated by [`ai-workflow/generate-sample-log.py`](ai-workflow/generate-sample-log.py). The real log contains named employers and my private assessment of each, so employer names throughout the published instruction files are stable pseudonyms (`Company-01`…), and compensation thresholds are role tokens (`FLOOR`, `TARGET`, `VETO_LINE`) rather than figures. Screenshots have company and role columns redacted. The engineering is unmodified.

## The architecture, and the one decision that shaped it

```
OneDrive/SharePoint CSV  ──shortcut──▶  Lakehouse (JobSearch_LH)
                                              │
                                    Dataflow Gen2 (JD_Transform)
                                    parse · split · unpivot · merge
                                              │
                                              ▼
                                 Fabric SQL Database (JobSearch_DB)
                          Fact_JobPostings · Bridge_ScoreComponents
                          Fact_Messages    · Fact_WriteBack (append-only)
                                              │
                                   automatic OneLake mirroring
                                              │
                                              ▼
                              Direct Lake semantic model → Power BI
                                              ▲
                                              │ Translytical Task Flow
                                   User Data Function (Python) ── write-back
```

**Why a Fabric SQL Database rather than a Lakehouse table.** Write-back was in scope from the start, and Fabric SQL Database is the only Fabric item type with enforced primary keys and reliable row-level `UPDATE` targeting — Lakehouse and Warehouse SQL endpoints don't support that. It still feeds Direct Lake, because Fabric SQL Database mirrors its tables into OneLake automatically. Mirrored Azure SQL and Mirrored SQL Server were both considered and rejected: they are read-only analytics mirrors of an externally hosted database, not a place to provision writable data, and either would have added a second database service for no benefit.

**Why Translytical Task Flows rather than an embedded Power App.** Power Apps needed a separate Developer Plan signup and the premium SQL Server connector, renders in an iframe that doesn't inherit report theming, and puts the write logic in Power Fx. TTF is native Power BI visuals with no additional licensing, and the write logic is a real Python Fabric item.

## Finding 1 — The write-back merge was ambiguous, and the ambiguity cost me the data

Four fields are user-owned: `Carls_Action`, `Carls_Action_Date`, `Outcome`, `Reason`. They exist **both** as columns in the source CSV and as columns the report writes to directly. Every refresh has to decide which wins.

The first design asked "does SQL already have a value?" That is the wrong question, and it fails in both directions:

- **CSV edits stopped working.** Once *any* value landed in SQL — including one the dataflow itself had just written from the CSV — later CSV edits to that row became silent no-ops. The merge treated "has a value" as "was written from the report".
- **A dropped table looked identical to a fresh one.** Both produce nulls. See Finding 2.

The fix was to track **origin, not presence**: a flag set only by the write-back function, so the CSV wins unless a genuine report write-back happened. That worked, and it is still the right idea — but storing the flag in the same table it protected is what turned a routine `DROP` into data loss.

## Finding 2 — A table that is its own only backup

`JD_Transform` writes to `Fact_JobPostings`, and its `Existing_WriteBack` query reads from that same table so write-backs survive the next refresh. That circularity is what made persistence work. It also meant the table was the only copy of its own history.

On 2026-08-26 the table was dropped and recreated while building an unrelated feature. The next refresh rebuilt it from CSV and wrote `WriteBack_Applied = false` across all 894 rows.

**The refresh did not merely fail to restore the data — it overwrote the evidence that the data had ever existed.** No error, no warning, and a table that looked completely healthy afterward.

Twelve rows were affected and all twelve were recovered, via Fabric's automatic point-in-time restore. But recovery worked only because the CSV happened to mirror every write-back — a property of how this workflow is used, not a safety net anyone designed. A write-back made from the report on a job the CSV never carried would simply have been gone.

**The redesign makes `Fact_JobPostings` genuinely disposable**, which is what it was assumed to be when it was dropped:

| Before | After |
|---|---|
| Write-backs stored in `Fact_JobPostings` | Append-only `Fact_WriteBack`, one full snapshot per write |
| Dataflow reads back from the table it writes | Dataflow reads `vw_WriteBack_Latest`; **the circularity is broken** |
| `WriteBack_Applied` stored — and droppable | Derived: presence in the log *is* the lock |
| Acceptance test: none | Drop and recreate the fact table; write-backs must return |

Full timeline, root cause, and the operational findings: **[Write-back data loss — post-mortem](https://carlwooldridge.github.io/fabric-portfolio/job-search-fabric/reference/writeback-incident-postmortem.html)** ([source](reference/writeback-incident-postmortem.html)).

Snapshots rather than deltas is a deliberate call: the write function does partial updates, so a delta log would need per-field "latest non-null" resolution to reconstruct state. Full snapshots make "latest row wins" correct and keep the read view three lines long.

## Finding 3 — Platform boundaries, each hit the hard way

| Boundary | What actually happens |
|---|---|
| **Data Activator cannot monitor a Lakehouse table at all** | Not a configuration gap. It accepts only event-based sources — Eventstreams, Real-Time Hub, Power BI visuals, KQL Querysets. OneLake events explicitly exclude shortcut-sourced data. The documented workaround is standing up an Eventhouse to diff each batch load, which is disproportionate infrastructure for a log that changes a few times a day. Abandoned in favor of a scheduled refresh, later supplemented by a Power Automate trigger. |
| **A table shortcut maps one *folder* to exactly one Delta table** | Dropping a second, differently-shaped CSV into a folder an existing shortcut already targets does not create a second table — it merges the rows into the existing table against the wrong schema, landing them as junk with unmatched columns null. The picker only allows selecting folders, never files, so there is no UI path to disambiguate. One CSV per folder, one shortcut per folder. |
| **Fabric's CSV reader is not multiline-aware** | Free-text fields with embedded newlines — RFC 4180-correct, correctly quoted, parsed fine by Python — still shatter, because Fabric ends a record at an embedded newline regardless. 15 logical rows became 376 physical lines. Fixed upstream by flattening line breaks to a ` ¶ ` marker and restoring them in DAX. |
| **Direct Lake cannot frame a SQL view** | And adding one to an otherwise-Direct-Lake model falls the **entire model** back to DirectQuery, not just that table. `vw_WriteBack_Latest` is therefore deliberately *not* in the model; the model reads the raw log table and does the latest-row reduction in DAX. |
| **Grouping/binning is unavailable over a live connection** | Power BI's `New group` feature is report-level and unsupported when connected live to a semantic model — it isn't in the menu at all. Histogram buckets are computed as real columns upstream, with a numeric sort key alongside the text label. |
| **UDF parameters must be camelCase** | `job_id` is rejected; `jobId` is required. Documented, but easy to lose an hour to. |
| **A data function button set via `Title` is unclickable** | The button renders, shows its tooltip, and silently does nothing. Setting the label as button text rather than `Title` fixes it. |

## Finding 4 — A DAX bug where every component inspected clean

The report needed to show a write-back *immediately*, before the next dataflow refresh folded it into the fact table. That means reading the log table live in the model:

```dax
Latest WriteBack ID =
CALCULATE(MAX(Fact_WriteBack[WriteBack_ID]),
          ALLEXCEPT(Fact_WriteBack, Fact_WriteBack[Job_ID]))
```

It returned the wrong answer for 8 of 9 jobs — every job got the same global maximum, so every `Latest *` measure came back blank and every `Effective *` measure silently fell through to the stale fact-table column.

The measure was right. The relationship was right — active, correct cardinality, correct direction. The data was right. No field was bound to the wrong table. Each was verified independently against the live model.

**`ALL` and `ALLEXCEPT` operate on a table's *expanded* table.** Across a many-to-one relationship, that silently includes the related "one" side. So `ALLEXCEPT(Fact_WriteBack, Fact_WriteBack[Job_ID])` cleared filters across the whole `Fact_WriteBack` + `Fact_JobPostings` space — and the single column it was told to preserve, `Fact_WriteBack[Job_ID]`, is a *different column object* from the one every visual actually filters on, `Fact_JobPostings[Job_ID]`. Nothing was preserved.

```dax
ALLEXCEPT(Fact_WriteBack, Fact_WriteBack[Job_ID], Fact_JobPostings[Job_ID])
```

**The general lesson:** when using `ALLEXCEPT` on the many side to isolate one key, and your visuals filter from the one side — which they almost always do — name *both* columns. Everything else can check out clean while the interaction is wrong.

## Finding 5 — Parsing an LLM's prose into a star schema

The score components aren't columns in the source. They're embedded in a sentence:

```
Score 62 = Lane 12 + Scope 8 + Comp 12 + Location 10 + Skills 14 + Applicants 6.
Capped from 78 ...
```

Validated against the real data before being trusted: **93.9%** of rows carry a parseable formula (the rest are genuinely unevaluated and correctly blank), with per-component hit rates of 90–100% for six of seven components. Perks lands at ~43% — which is correct, not a parse failure; it is simply omitted from the formula that often.

**Capped scores get a deliberate two-tier treatment.** 26% of rows carry "capped from" language whose arithmetic does not reconcile against the visible components — a pre-existing quirk of how those notes were generated, not a parsing bug. Deductions are computed only for the 74% where the maths actually closes; capped rows show their named components with no forced (and misleading) deduction. `Pts_Deductions` is therefore null on those rows by design, and the unpivot filters them out rather than writing meaningless blank component rows.

Everything derived — comp splits, location splits, applicant-volume parsing, day buckets — is computed in Dataflow Gen2, because **Direct Lake supports neither Power Query transformations nor calculated columns.** That constraint is what makes this an ETL project rather than a modeling one.

## The AI workflow that feeds it

The pipeline upstream of Fabric is the part I'd point at first. It ingests job-alert mail, fetches postings, dedupes against the log, evaluates each against a scoring rubric, and writes the row.

**The rubric is calibrated by measurement, not preference.** A rule earns veto status only where my own override rate is at or near zero:

| Rule | Fired | Applied anyway | Override rate | Disposition |
|---|---|---|---|---|
| Third-party board post | 26 | 0 | 0% | keep veto |
| Named consulting firm | 28 | 0 | 0% | keep veto |
| Comp below `VETO_LINE` | 26 | 1 | 4% | keep veto |
| Contract / fixed-term | 22 | 10 | **45%** | → deduction |
| Consulting, by JD language | 52 | 25 | **48%** | → deduction |

Two rules I had believed in turned out to be coin flips, and the data said so. The comp floor and the veto line are deliberately *different numbers* for the same reason: raising the veto to the floor would have blocked 22% of the applications I actually made.

**It measurably improved.** A threshold change on 2026-08-10 moved Pursue precision from 43% to 75% and eliminated all 36 sub-70 false positives — at a recall cost that showed up honestly in the other column, as 70 skipped rows I applied to anyway. That population is what the fourth verdict, `Review`, was added to serve: keying on a *compensable* gate firing surfaces 53% precision against a 20% base rate, where score bands alone were flat at 18–22% across the entire range.

Design spec for the self-correcting loop and the cost model behind it: **[The Verdict Loop](https://carlwooldridge.github.io/fabric-portfolio/job-search-fabric/reference/the-verdict-loop.html)** ([source](reference/the-verdict-loop.html)).

**Credential hygiene, since this touches mail and a browser session.** Nothing is stored in the repository or the scripts: the IMAP password is read from the macOS Keychain at runtime, browser session state is written outside the project tree, and every Fabric call mints a short-lived token from an existing `az login`. [`ai-workflow/scripts/mail-imap.py`](ai-workflow/scripts/mail-imap.py) is the reference implementation.

## What this is *not*

**It is not real-time, and saying so precisely matters more than the adjective.** Nothing here is push-based streaming. Freshness is the sum of a ~15-minute OneLake shortcut cache for SharePoint/OneDrive sources plus the dataflow's own refresh interval — call it 15–45 minutes end to end. The one exception is the write-back path, which reads the log table live in the model and appears immediately.

**The report is not the system of record.** The CSV is, and the SQL database is a derived copy — with the single exception of `Fact_WriteBack`, which exists nowhere else and is the reason that table carries a "do not drop" header.

---

## Deliberately not done

- **Recency-based conflict resolution.** Once a report write-back exists for a job, later CSV edits to those fields are ignored. Comparing `Carls_Action_Date` on both sides would fix it; it hasn't been needed.
- **A stacked funnel.** Power BI's funnel visual has no legend well, and the documented workaround — a stacked bar with a white padding series faking the taper — leaves invisible-but-clickable segments. Rejected as a hack stacked on a Direct Lake calculated-table restriction.
- **Fixing the source CSV's comma quoting.** The writer uses naive string joining rather than a real CSV writer, so embedded commas can break column alignment. Diagnosed, not yet fixed at source.
- **Outcome as a learning signal.** Only 28 applications have a known outcome and effectively all are rejections. Zero variance is zero signal; feeding it to the rubric learner would produce confident nonsense.
