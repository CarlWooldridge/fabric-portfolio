The table that was its own only backup

A DROP and recreate destroyed every report write-back in the system. The data came back — but only because of a coincidence, and that is the part worth writing down.

Incident 2026-08-26 Recovered same day Rows affected 12 Permanent loss none Redesigned 2026-08-27

Summary: dbo.Fact_JobPostings was dropped and recreated while building an unrelated feature. The next scheduled dataflow refresh rebuilt it from CSV and, in doing so, silently erased the evidence that any write-back had ever existed. No error was raised. The table looked completely healthy afterward.

Part One

What happened

  • 16:54:55Fact_JobPostings is dropped and recreated. The semantic model's Direct Lake framing immediately begins failing — five consecutive DirectLake_TableNotFound errors between 16:54:55 and 16:55:35, visible in the model's refresh history.
  • 16:55:15The new, empty table is created. sys.objects.create_date still records this moment — the catalog remembers what notes forget.
  • ~17:00The next JD_Transform refresh runs. It rebuilds the table from the source CSV and writes WriteBack_Applied = false across all 894 rows.
  • laterA pull of the action fields is taken and saved to scratch/. It looks like a pre-drop backup. It is not — see below.
  • recoveryPoint-in-time restore to a pre-drop timestamp creates JobSearch_DB_backup, which still holds the 12 rows with their flags intact.

The false lead

scripts/fabric-pull-actions.py had produced a CSV that appeared to be a snapshot taken before the drop. It was not: the script issues a live DAX query through the semantic model, so it reflects whatever the table holds at the moment it runs. Pulled after the drop, it faithfully returned post-drop state. A file that looks like a backup, is named like a backup, and is dated plausibly — and contains none of the data you need.

Part Two

Root cause: the self-referencing dataflow

JD_Transform contained two queries that, between them, closed a loop:

  • Fact_JobPostings — reads the CSV-derived Lakehouse table, transforms it, and writes to JobSearch_DB.dbo.Fact_JobPostings.
  • Existing_WriteBack — reads from that same SQL table, so that values written from the report survive the next refresh.

That circularity is exactly what made write-back persistence work. It also meant the table was the only copy of its own history.

The failure turns on a single line, and on a comment that was correct about the mechanism while being wrong about the consequence:

NormalizeFlag = Table.AddColumn(Expanded, "WriteBack_Applied",
                                each [WB_Applied] = true, type logical),

// WB_Applied is null on first run (empty table) or for any Job_ID never
// touched by a real write-back — treat null the same as false.

An empty table and "no write-back ever happened" are indistinguishable

Both produce null. The refresh could not tell a dropped table from a clean slate, so it treated a catastrophic loss as a normal first run.

Each step behaved exactly as designed. The composition is what failed.
StepResult
Table dropped and recreatedSQL-side write-back values gone
Existing_WriteBack reads itreturns empty / all nulls
NormalizeFlagWriteBack_Applied = false on all 894 rows
ResolveText / ResolveDatelocked = false → CSV wins on every row
Destination write (Replace)table repopulated from CSV alone, all flags false

The refresh did not merely fail to restore the data. It overwrote the evidence that the data had ever existed. There is no error, no warning, and no degraded state to notice — which is what makes this failure mode worth more than the twelve rows it cost.

Part Three

Why recovery worked, and why that is not reassuring

Two things saved this. Neither was designed to.

1. Fabric's automatic point-in-time restore

SQL databases in Fabric take full, differential and log backups with a 7-day PITR window, on by default, working on trial capacity. Restore creates a new database rather than overwriting the original, so the operation is non-destructive and safe to attempt under pressure. It cannot restore across workspaces or regions, and deleting a database mid-restore cancels it unrecoverably.

2. The CSV happened to mirror every write-back

Comparing the 12 restored rows against the source CSV found zero differing cells. Production already held the correct values, because the dataflow had written them back in from the CSV. Only the WriteBack_Applied flag was actually lost, and a 12-row UPDATE repaired it.

This is the finding, not the recovery. Nothing in the architecture guaranteed the CSV would mirror the write-backs — that was a property of how this particular workflow happened to be used, not a safety net anyone designed. A write-back made only from the report, on a job the CSV never carried, would simply have been gone.

Part Four

The fix: make the fact table genuinely disposable

The error was not the DROP. Fact_JobPostings is a derived table — every column in it can be rebuilt from the CSV and the transformation logic. Treating it as disposable was correct. It just wasn't true, because write-backs were living in it.

Write-backs are source data. They belong somewhere the dataflow only ever reads.

An append-only log

dbo.Fact_WriteBack records one row per write-back event and is never updated or deleted from. Each row is a complete snapshot of all four user-owned fields after that write, not a delta — because the write-back function performs partial updates, and a delta log would need per-field "latest non-null" resolution to reconstruct current state. Full snapshots make "latest row wins" simply correct, and keep the read view three lines long.

CREATE VIEW dbo.vw_WriteBack_Latest AS
SELECT Job_ID, Carls_Action, Carls_Action_Date, Outcome, Reason, Written_At
FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY Job_ID ORDER BY WriteBack_ID DESC) AS rn
    FROM dbo.Fact_WriteBack
) t
WHERE rn = 1;

The one-line change that breaks the circularity

Existing_WriteBack now navigates to vw_WriteBack_Latest instead of Fact_JobPostings. The dataflow no longer reads back from the table it writes.

Presence replaces the stored flag

WriteBack_Applied stops being a stored column that can be lost in a DROP and becomes derived: if a job appears in the log at all, a genuine write-back happened.

NormalizeFlag = Table.AddColumn(Expanded, "WriteBack_Applied",
                                each [WB_Job_ID] <> null, type logical),

Why this specifically closes the hole

The original ambiguity was between "no value recorded" and "value lost". A computed value cannot be lost in a drop the way a stored one can — there is no longer a state in which the system silently forgets that write-backs existed. The failure mode is designed out rather than guarded against.

The acceptance test is the scenario that caused the incident: drop and recreate Fact_JobPostings, run the dataflow, and confirm the write-backs come back. Passing it is what makes the table honestly disposable.

Part Five

Operational findings worth keeping

FindingDetail
Cross-database queries fail on the transactional endpoint Three-part naming returns Msg 40515. It works only on the read-only SQL analytics endpoint, which cannot be an UPDATE target. This is an endpoint limitation, not a tooling one — the Fabric SQL editor, VS Code and notebooks all fail identically. To reach the restored copy, open a second connection against it directly.
A live query is not a backup Any export that reads through the semantic model reflects current state by definition. If it runs after the loss, it captures the loss.
sys.objects is the honest timeline create_date and modify_date survive when memory and notes disagree. The OneLake mirror of a SQL table lags the table itself, so it is not a reliable "when did this change" source.
Refresh history is external evidence The semantic model's DirectLake_TableNotFound failures timestamp the outage from outside the database, independent of anything the database itself records.

What would have caught it earlier

  • An independent copy. The log is now the single source of truth for data that exists nowhere else, so it gets a periodic CSV export rather than relying solely on the 7-day PITR window.
  • A row-count assertion on the flag. "Write-back count dropped to zero" is a one-line check and would have fired on the first post-drop refresh.
  • Naming that carries the warning. Every other Fact_* table in this model is dataflow-owned and rebuildable. Fact_WriteBack is deliberately not, and its CREATE TABLE now says so at the top — because the assumption that a Fact_ table is disposable is exactly the assumption that caused this.
